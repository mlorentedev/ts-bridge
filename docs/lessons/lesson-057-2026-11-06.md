# 2026-11-06

**A rule that is present is not a rule that is enforced.** `host setup` read `ufw show
added`, found its allow, and reported the port as admitted, while `ufw status` said
`inactive` (#608). The added list is ufw's configuration; whether ufw runs is a separate
read. With ufw off the port was open because nothing filtered it, so `ok` described the
wrong cause and `firewall_ok` told the operator a firewall protected the host. Read the
running state before trusting the configured one, and report a firewall that is off as
something the operator must act on (`manual`), never as success. Enabling it stays theirs:
`ufw enable` can cut the SSH session they are using.

**Text reads of system tools need the C locale.** The host reads match English words
(`Status: active`, iptables' "No chain/target/match by that name"). ufw and iptables are
gettext-translated, so on a host whose root shell runs in another language every such match
fails quietly: a missing chain looks like a refused read, and a status reads as neither
active nor inactive. `execRunner` now runs every command with `LC_ALL=C` and drops
`LANGUAGE`, which gettext lets outrank the locale. The fake runner in the tests cannot catch
this, so `TestExecRunnerReadsUnderTheCLocale` runs a real child process.

**A fixture map that answers "" for an unknown command hides new reads.** The recording
runner returns empty output for any command it was not given. Adding `ufw status` made every
existing ufw row fail on "printed neither active nor inactive", which is the right
strictness: each row now states the status it assumes instead of inheriting one by accident.
