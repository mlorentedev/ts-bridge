# 2026-10-22

**"Is there an allow?" is not "is the port open?". Read rules in the order the
firewall evaluates them.** A DROP or deny listed before the allow shadows it, so
`host check` reported `ok` on a blocked port. When no allow existed, `host setup`
appended one after the deny, where it never matches, and reported `changed`
(#481). Walk the rules in order and stop at the first one that decides the port.

**Let only the unambiguous rule decide against the operator.** "Deny the LAN,
allow Tailscale" puts a scoped deny before a scoped allow, and it is a correct
hardened ruleset. Only an unscoped deny (no interface, source or destination)
counts as blocking. A scoped deny is the operator's judgment, the same rule
BUG-035 applied to scoped allows.

**When the tool may not fix it, say `manual`.** Setup never deletes or
reorders firewall rules, so a blocking deny is `manual` in both setup and
check. It names the rule and leaves the edit to a person. That keeps setup from
reporting `changed` on a rule it knows cannot match.

**ufw's listing order is its evaluation order, and identical matches
replace each other.** On ufw 0.36.2, `ufw show added` prints rules in
`user.rules` order, `ufw insert` included. Adding `allow 3389/tcp` over an
existing `deny 3389/tcp` updates that rule in place ("Rules updated"), so the two
never coexist. A `deny 3389` (any protocol) and an `allow 3389/tcp` do. Measure
the listing before trusting its order.
