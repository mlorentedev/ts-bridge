# 2026-08-31

- **A gate that cannot answer is indistinguishable from a gate that says red — until nobody reads it anymore**: `dotf pr triage-queue` exited 1 in this repository for as long as the command existed here, and it did so for the wrong reason. The registry it consults, `harness/review-attestation.json`, was never created, so the answer was always `read reviewer registry: no such file or directory`. The exit status is deliberately 1 for *unanswerable* as well as *pending* — so a queue that cannot be computed is never mistaken for a clear one — but a check that reports one thing every time it runs stops being read, and the discipline it was supposed to enforce (`## Review triage` before calling PR work done) quietly became folklore. Fixing it was not writing code, it was porting two JSON files (see `harness/`). Rule: when a guard's verdict stops changing, verify the guard can answer the question at all before concluding anything about the answer — and prefer wiring the mechanism to restating the instruction. Same shape as `dotf spec archive` here: the spec-review gate is disabled by *absence* of `harness/reviewer-pool.json` (absent = "no opinion", not "nobody"), which means an unarchivable spec and a green-looking gate are both produced by the same missing file.

- **A closed issue can absorb an acceptance criterion that was never delivered, and the merge hides the remainder**: #212 (SEC-212) closed on 2026-08-15 with PR #298, and `specs/SEC-212-authkey-hardening/tasks.md` recorded AC3 ("update the deployment runbooks") as done. It was not: the Linux and multi-device runbook edits were still unstaged in the working tree of `feat/authkey-file-hardening`, which had lost its upstream when the PR merged, so nothing was pushed, reviewed or reverted. Three weeks later `docs/runbooks/guide-deployment-linux.md` still told operators to put `TS_AUTHKEY` in the systemd `EnvironmentFile` — the exact pattern the ticket existed to retire. Rule: verify an acceptance criterion against the **artifact**, not against the issue's state. A closed issue plus a merged PR proves a diff landed, never that the promise was kept; and a branch whose upstream is `gone` is a signal worth reading as "what did I leave in this working tree?" before deleting anything.

- **Documentation is only as true as the last time it was executed**: recovering that uncommitted work nearly shipped a runbook example that did not exist — `ts-bridge init --auth-key-file <file>`. `connect` registers that flag; `init` does not, so the command fails with `unknown flag: --auth-key-file` (exit 1, measured against a binary built from master). The write-up of a security recommendation is where a reviewer cannot easily follow, so the check is one line of shell: build, run the documented command, read the exit status. The gap is real and now tracked as #306; the runbook shows the masked interactive `init` prompt instead, and names `connect` as the only key-file consumer.

- **A reviewer that cannot be reached is indistinguishable from a reviewer that said "clean" — verify it can answer, and say what you have and have not proven**: CodeRabbit's per-hour limit made it a second, quieter gate failure in this repo (17 of 29 recent PRs *Declined*). Before wiring a second reviewer (PR-Agent, #314) I measured its attesting marker (`## PR Reviewer Guide`) across the sibling repos that already run it — 215 hits in kubelab, 172 in dotfiles, all posted by `github-actions[bot]` — rather than copying the string from a config I had not seen fire locally. And the registry entry records the asymmetry: proven there, **unproven here** until this workflow's first green run. A marker declared but never matched is the silent version of the declined CodeRabbit review — the queue reads "clear" while nothing reviewed. Rule: give every review signal a marker, match the marker from the base ref, and gate merge on the marker's presence so an absent reviewer is red, not green. Kid rule version: a sentry who cannot see anything is not keeping watch.
