# 2026-08-07

- **A precedence test whose winning value equals the default cannot tell you the layer won**: `TestMergeFullPrecedence` set the flag to `30s`, which is `defaultTimeout`, and asserted the result was `30s`. Its own comment gave it away — `// Flag (30s) > Env (1m) > YAML (3m) > Default (30s)` — first and last value identical. It still constrained something, because env supplied `1m`, but the assertion could not distinguish "the flag layer won" from "the default survived", which is the exact question a precedence test exists to answer. Rule: every layer in a precedence case needs a value that is unique **and** different from the default; assert that property of the test table itself if the table is generated, so a future edit cannot quietly reintroduce the collision. The wider version: whenever an assertion's expected value coincides with the value the system would hold if the code under test did nothing, the test is compatible with the code doing nothing.

- **Fewer than half the fields were ever discriminated, and coverage could not say so**: `Merge()` applies ~17 configuration fields, each behind its own guard; the tests asserted precedence for two of them. Line coverage was green throughout — every guard *executed*. What surfaced the gap was mutation testing: 43 surviving mutants clustered in exactly the per-field apply guards, 25 `CONDITIONALS_NEGATION` (killed by unique per-layer values) and 18 `CONDITIONALS_BOUNDARY` (killed only by explicit zero rows, because `> 0` → `>= 0` differs from correct behaviour *only* at zero). Rule: the two mutant classes need different case designs, so "add unique values per layer" alone leaves a third of the survivors alive. Reading where the boundary mutants clustered also found a production bug (#282) that no test had been written for yet — the mutants did not identify the defect, but they marked the line it lived on.

- **`timeout-coefficient` does not transfer between a whole-module and a single-package mutation run**: `.gremlins.yaml` pins `timeout-coefficient: 3`, calibrated in CI against the full module. Narrowing a local run to one package produced **206 of 243 mutants `TIMED OUT`** — the per-mutant timeout appears to include compiling the mutated package, which the baseline measurement does not, and a small package's baseline leaves no headroom for it. `--timeout-coefficient 200 --workers 2` gave 0 timeouts in ~50s. Rule: a `TIMED OUT` verdict is *absence of data*, not a killed mutant — a narrowed run read without checking that column looks exactly like an efficacy collapse, and a run with mass timeouts is not evidence of anything in either direction.
