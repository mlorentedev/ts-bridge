# 2026-11-14

**When several processes share a file, publish each artifact once and never append to it together.**
LOG-788 (#788, #816) made the log rotator safe for several ts-bridge processes writing one day's
log. The first two designs claimed a day by renaming its `.log`, then appended a gzip member to the
shared `ts-bridge-<day>.log.gz`. Round 1 of the independent review found that a claim whose
compression failed was never retried and could be aged out. Round 2 found that the retry let two
processes append to the same archive at the same time. Their gzip members interleaved and the day was
lost, while the spec described the outcome as "duplicated lines". Only `test-windows` showed it
(`flate: corrupt input before offset 1`). The macOS and Linux runs passed on timing. Round 3 removed the
shared writer:

- every compression writes its own `.gz.partial`;
- it publishes it with `os.Link` to the day's name, which never overwrites an existing file;
- if that name is taken, it falls back to a unique name;
- only claims older than an hour are retried;
- retention deletes archives only.

Two general rules came out of it. A "retry" that can run at the same time as the first attempt is a
second writer, so make the artifact write-once before adding retries. And when a concurrency test
passes on one OS and fails on another, treat the failure as the true result. Do not treat it as noise.
`rotator_test.go`'s concurrency test still exercises only the claim, not two parallel archive writes;
strengthening it is #817.
