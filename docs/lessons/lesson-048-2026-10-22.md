# 2026-10-22

**A merge that reports one conflict can leave others staged as content.** In #485
a `git merge origin/master` stopped on a conflict; one file was resolved and
`git add -A` staged the two files still holding markers as if they were
resolved. Every check stayed green, including the lessons guard that reads the
index the markers corrupted: a guard that parses a file is not a guard against
that file being corrupt. `scripts/check-conflict-markers.sh` now fails on any
tracked line that starts with one of the three markers Git writes around a
conflict's sides: the open marker (`<`), the close marker (`>`) and the diff3
base marker (`|`), each a run of seven or more (#491).

**Match the markers that frame a conflict, not the separator.** Git writes the
open and close markers around every separator (and around a diff3 base), so
they cover every real conflict; the base marker is matched too, so a
half-resolved diff3 hunk cannot slip through. The separator alone (seven `=`) is also a valid Markdown setext
underline, so matching it buys no coverage and adds the one false positive.

**A guard over every tracked file cannot have its fixtures committed.** A
marker-bearing fixture under `scripts/tests/fixtures/` would red the real tree
the moment it landed. The suite builds throwaway repositories at runtime and
assembles the markers with `printf | tr`, so no file in the repo holds one at
column 0. The same applies to docs that quote a conflict: indent the example.

**`git grep` exit 1 means no match.** Under `set -e` it aborts the script, and
treating every non-zero status alike reads an error (no repository) as a clean
tree. Capture the status and fail closed on anything above 1.
