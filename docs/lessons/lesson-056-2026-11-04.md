# 2026-11-04

**Bind a secret to the endpoint it was issued for, not to the name that points at it.** A
profile stored a credential reference and a control URL as two independent fields, so
anything that changed one left the other behind: a re-imported `tsb://` descriptor moved the
profile to a new `cp=` and kept the key, and a `TS_CONTROL_URL` in `./.env` outranked the
profile while the profile's key was still loaded (#617). Each field was correct on its own.

**Check the resolved value, not the layer you expect to win.** `connect` loads `./.env`
before the profile, and the profile is the lowest layer, so "the profile says X" proves
nothing about where the key goes. The guard reads the layers above the profile (flag,
environment, YAML) before the profile fills the YAML slot, because that fill erases which
layer set the value. A refusal that names both URLs and the layer is also the diagnostic.

**Every writer needs the guard, and the test must enumerate them.** `Import`, `Configure`
(`init --profile --force`) and `Set` all rewrote `ControlURL`. One table runs all three
against the same cases, so a fourth writer that skips `bindCredential` shows up as a
missing row instead of a quiet hole. Existing tests had encoded the bug as setup (a
credential attached, then the control URL changed under it); they now build the profile in
the order a real one is issued.
