# 2026-10-22

**An exact-match probe answers a narrower question than the one you are asking.**
`iptables -C INPUT -p tcp --dport 3389 -j ACCEPT` asks "is this exact rule
present", not "does an allow cover the port". A Tailscale-scoped allow
(`-i tailscale0`) fails that probe, so `host setup` appended an unrestricted
ACCEPT and widened access the operator had narrowed (#479). Read the rule set
(`iptables -S INPUT`) and decide coverage per rule instead.

**`iptables -S` prints its own syntax, not what was typed.** On iptables 1.8.10
(nf_tables) `--dport 3389` prints as `-p tcp -m tcp --dport 3389`, other matches
can come before the port, a negation prints before its flag (`! --dport`), and a
comment keeps its quotes with inner ones escaped. Look flags up by name, check
the token before each for `!`, and remove the comment value before splitting.
Capture the real output in a container before writing the parser; three review
rounds on the ufw parser came from edge cases nobody had printed.

**A jump in `INPUT` is normal on a Tailscale host.** tailscaled's iptables mode
creates `ts-input` and adds `-A INPUT -j ts-input` (`tailscale.com/util/linuxfw`).
A rule that treats any jump as "the allow might be hidden there, so do nothing"
would leave every native Tailscale host stuck. Check what the platform you
target puts in the chain before deciding what a jump means.
