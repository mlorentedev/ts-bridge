# 2026-11-17

**`ReadHeaderTimeout` alone does not bound a Go HTTP request: an announced body that never arrives
holds the connection, and `Shutdown(context.Background())` waits for it forever.**
The audit of v2.0.0 (#78, item 1 and 6 of #807) flagged the PAC server and the health server. Both set
only `ReadHeaderTimeout`. A client that sends complete headers with `Content-Length: 100` and no body
gets no response at all: when a handler leaves a small body unread, `net/http` discards it *before*
writing the response headers, so it blocks reading. The connection stays `StateActive`, which
`Shutdown` waits for, and nothing times it out. The regression tests reproduce it in under a second
with a shortened `ReadTimeout`.

Rules: an `http.Server` that faces anything but the process itself sets `ReadTimeout`, `WriteTimeout`
and `IdleTimeout`, not just `ReadHeaderTimeout`; and every `Shutdown` gets a bounded context with a
`Close` fallback, because a graceful stop that can wait forever is not a stop.
