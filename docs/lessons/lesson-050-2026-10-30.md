# 2026-10-30

**A jump is where the answer lives, not a rule to skip.** With
`--netfilter-mode=on`, tailscaled inserts `-A INPUT -j ts-input` and keeps its
`-i tailscale0 -j ACCEPT` one chain down. Reading only `iptables -S INPUT`
treated the jump as opaque, so on the most common host `host setup` appended
an ACCEPT that opened RDP on every interface and added no tailnet reachability
(#492). Read the chain that the jump names, and evaluate its rules at the
jump's position. That is where a packet meets them: a deny before the jump
still decides first, and a deny after it is shadowed.

**Follow only the jump whose meaning you know.** Only the unqualified jump that
tailscaled writes is inlined. A jump with `-i`/`-s` applies the chain to part of
the traffic, and other chains (docker, fail2ban) have unknown contents, so both
stay opaque. A wider walk would turn an unknown chain into a claimed allow.

**Pin the printed form, and say how it was obtained.** The fixture comes from
tailscale.com's own rule builders (`AddChains`, `addBase4`, `AddHooks`, …),
replayed in order and printed by iptables 1.8.10. That pins how `iptables -S`
prints the rules, not what a running tailscaled does, and the spec says so. A
second read that fails is unknown, never "absent", so setup cannot widen on a
guess.

**Correction (2026-11-01, #532): opaque must mean unknown, not absent.** The
qualified jump stayed opaque, but "opaque" was read as "no rule": the port
came out absent and `host setup` appended the very ACCEPT on every interface
that #492 removed. An exact-shape matcher fails open on every other shape. The
sibling path, a failed read of `ts-input`, already failed closed. Now the walk
stops at any jump or goto into `ts-input` other than tailscaled's unqualified
one. What the rules before it decide still stands, so a deny there is still
named. If they decide nothing, the read is unknown: check reports `unverified`
and setup appends nothing. Cutting the walk at the jump keeps every answer the
old walk got right. Failing on the jump's mere presence would have turned a
correctly named deny into `unverified`. An opaque jump into another chain
(docker, fail2ban) still never decides, because only `ts-input` is known to
hold the tailnet allow.

**Correction (2026-11-02, #540): cut the output into rules once, at the read.**
Each reader split `iptables -S` on newlines itself and only then blanked quoted
values. A `--comment` that holds a newline prints raw (`xtables_save_string`
escapes only `\` and `"`), so the text after it read as a rule. A comment that
spells an ACCEPT for the port then came out as an allow, which fails open.
`iptRules` now turns such newlines into spaces before any reader sees the
output, for INPUT and for `ts-input`. Quote blanking is still per line; what
changed is that a line is now always a whole rule. An unterminated quote is not
iptables' output, so it is left as printed rather than allowed to swallow the
rules after it.
