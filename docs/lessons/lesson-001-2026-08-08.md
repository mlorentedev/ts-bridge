# 2026-08-08

- **Mutation-checking a guard proves it catches the *old* defect, and says nothing about what your fix newly breaks**: fixing #282 meant replacing `if flags.IdleTimeout >= 0` with `if flags.IdleTimeout != nil`. The new test was verified the right way — the bug was reintroduced deliberately and the test went red — so the guard was known to work. It was still an incomplete check, by construction: reintroducing the original defect can only ever exercise the failure mode you already understand. What the reviewer caught, and the mutation check could not, was a *second* defect the fix itself created — a negative `--idle-timeout` had been silently discarded by `>= 0` and was now applied, so `--idle-timeout=-1s` would reach the proxy and expire every connection immediately. Rule: "I reintroduced the bug and the test failed" establishes the guard's lower bound, not the change's safety. The complementary question — *what did my change stop rejecting?* — has to be asked separately, and a comparison operator swapped for a nil check is exactly where to ask it.

- **A comparison guard can be doing two jobs with only one of them documented**: `if flags.IdleTimeout >= 0` was written to answer "did the user supply this flag?", and its comment said so. It also, incidentally, filtered out every negative value — a second job nobody had written down, because for a `time.Duration` the unset check and the sign check happen to be the same expression. Swapping the value guard for a pointer guard preserved the documented job and silently dropped the undocumented one. Rule: before changing the *representation* behind a guard, enumerate every input the old expression rejected, not just the one it was written for. `>= 0`, `> 0`, `!= ""` and `!= nil` all conflate presence with validity to different degrees, and the conflation is invisible until the representation changes. The fix here was to make the second job explicit — `validateIdleTimeout` now mirrors the `validateDialRetries` that already existed for the sibling field.

- **A test that builds its input by hand cannot see a defect in the code that builds that input**: `TestPrecedenceIssue282UnsetNumericFlagsClobber` calls `Merge(PartialConfig{}, FlagSet{})` and asserts env survives. It is a correct test and it passed the moment the merge guards were fixed — but with the production bug fully restored in `collectFlags`, it *still passed*, because it never crosses `collectFlags`. It was asserting that `Merge` honours a `nil` nobody guaranteed would arrive. The defect lived in the seam between the flag parser and the merge, and only a test that starts from the real `cobra.Command` can stand in that seam. Rule: when a bug spans "who produces the value" and "who consumes it", a test constructing the value directly tests half the bug; locate the test at the boundary the defect actually crosses, and confirm which half each test guards by breaking each half in turn.
